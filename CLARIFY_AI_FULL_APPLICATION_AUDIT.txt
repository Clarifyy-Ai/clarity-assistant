1.1 WHAT THIS APPLICATION IS
----------------------------
Career Pilot is an AI-powered interview preparation and rehearsal platform with a
second, largely separate product line for Indian government / competitive exam
MCQ mock tests. It ships as:

  (a) a web application (React SPA, Vite build, Supabase backend), and
  (b) a Windows/macOS/Linux Electron desktop app that is deliberately
      overlay-only — the desktop build boots straight into a floating
      always-on-top coaching overlay and pushes every other page out to the
      system browser.

The core value proposition in code: during a real or practice interview, the app
listens to microphone plus system/tab audio, transcribes both sides with
Deepgram, separates interviewer from candidate, and pushes AI-generated hints and
full answers into a floating overlay in near real time. Around that core sit
preparation tools, a document/resume system, an answer library, scheduling,
company research, analytics, debriefs, a credits-based billing system, an admin
back office, and the gov-exam test engine.

1.2 HEADLINE VERDICT
--------------------
This is a genuinely large, genuinely built application — not a prototype. The
core loops (auth, onboarding, live coaching, mock interviews, debriefs,
documents, credits, Stripe/Razorpay checkout, gov-exam tests, admin) all execute
against real Supabase tables and real AI providers.

However it is NOT uniformly finished. The audit found three consistent patterns
of incompleteness:

  1. DUPLICATE / ABANDONED PATHS. Several fully-written backend endpoints are
     never called because the frontend later chose to write to the database
     directly instead (end-session, save-answer, save-transcript, ai-feedback,
     billing-status, generate-practice-questions, validate-api-key). Similarly
     three Settings page components exist with no route.

  2. CLIENT-SIDE GATES WITHOUT SERVER ENFORCEMENT. The UI blocks free users from
     paid features, but the server-side plan check is effectively a no-op
     because the "starter" tier is ranked equal to "free" and almost every
     capability is ranked 0.

  3. DISPLAY-ONLY ADMIN AND SETTINGS SURFACES. Some admin actions and several
     settings toggles save nothing, or save a value that no code ever reads.

1.4 THE TEN THINGS THAT MATTER MOST
-----------------------------------
  1. Server-side plan gating does not actually gate. PLAN_RANK gives "starter"
     the same rank (0) as "free", so requirePlan(...,"starter") lets free users
     through. Almost all capabilities are also rank 0.
     supabase/functions/_shared/billingCatalog.ts:47-53,
     supabase/functions/_shared/requireCapability.ts:24-37

  2. Three AI endpoints burn money with no credit charge: parse-resume,
     gap-analysis, parse-document — even though creditEconomics.ts defines
     resume_analysis = 12 credits.

  3. Buying the top plan ("Max"/enterprise) through Stripe fails, because the
     client PLANS object has no stripePriceIdMonthly for enterprise.
     src/lib/billing/subscriptionManager.ts:364-399

  4. Admin revenue numbers are wrong. monthlyRevenueByPlan sums
     credit_transactions.amount (a credit count) and formats it as money.
     src/lib/supabase/database.ts:1314-1321, AdminRevenue.tsx:372,499

  5. A failed Stripe invoice sets profiles.credits to an absolute 50, which can
     erase purchased credit packs.
     supabase/functions/stripe-webhook/index.ts:573-574

  6. Razorpay "pro_monthly" is a one-time Order, not a subscription. Indian
     customers get one month and never auto-renew, and cancel/resume do not
     apply to them.

  7. .env.production is committed to git with a live Supabase anon JWT, and the
     ~86 MB release-new/ installer output is untracked but NOT gitignored.

  8. CI would fail today: the workflow sets VITE_APP_ENV=test and
     ci-placeholder* values, both of which scripts/validate-env.js rejects.

  9. The gov-exam product has an engine but almost no content: about 26 MCQs are
     seeded by SQL. Everything beyond that depends on admin imports or a scraper
     service that is not deployed.

 10. India-only gating is switched off in code (indiaRegion.ts returns true
     unconditionally) while the UI still advertises the restriction.

PART 3 — THE FIVE PORTALS
================================================================================

The application is not one interface. It is five distinct surfaces with
different shells, different guards, and different audiences.

PORTAL 1 — PUBLIC MARKETING SITE
  Audience ....... anonymous visitors, search engines
  Shell .......... MarketingLayout (own header + footer)
  Guard .......... none (wrapped only by ElectronRouteGate)
  Loading ........ EAGER (deliberately not lazy, for first-paint speed)
  Pages (11) ..... / (Landing), /pricing, /gov-exams, /help, /help/:slug,
                   /shortcuts, /blog, /blog/:slug, /terms, /privacy,
                   /share/:token (public shared debrief/scorecard)
  Verdict ........ FULLY IMPLEMENTED. Help and Blog are database-backed with a
                   hardcoded fallback file for Help only.

PORTAL 2 — AUTHENTICATION AND ONBOARDING
  Audience ....... new and returning users
  Shell .......... bare full-screen pages, no chrome
  Guard .......... none on auth pages; /onboarding requires login only
  Pages (7) ...... /login, /signup, /verify-email, /forgot-password,
                   /reset-password, /auth/callback, /onboarding
  Verdict ........ Auth FULLY IMPLEMENTED; onboarding PARTIAL.

PORTAL 3 — MAIN USER APPLICATION
  Audience ....... signed-in, email-verified, onboarded users
  Shell .......... AppShell = sidebar + top bar + mobile nav + modals
  Guard .......... ProtectedRoute requireOnboarded requireEmailVerification
  Pages .......... ~70 routes across 15 functional modules plus 19 settings tabs
  Verdict ........ Core FULLY IMPLEMENTED; per-module detail in Part 6.

PORTAL 4 — ADMIN BACK OFFICE
  Audience ....... users with the 'admin' role in user_roles
  Shell .......... AdminLayout — a completely separate shell, no user sidebar
  Guard .......... double-gated: outer ProtectedRoute + inner requireAdmin +
                   AdminLayout's own redirect
  Pages (15) ..... dashboard, users, analytics, revenue, model-costs,
                   feature-flags, seed-questions, bulk-upload, live-chat,
                   questions (+ :id), audit-log, qa-checklist, support,
                   promo-codes, billing-settings
  Verdict ........ MIXED — see 6.22. Core management works; three surfaces are
                   read-only, fake-save, or localStorage-only.

PORTAL 5 — DESKTOP OVERLAY (ELECTRON)
  Audience ....... desktop users during a live interview
  Shell .......... chromeless, always-on-top, 480x640, hash router
  Guard .......... ElectronRouteGate — an allowlist. Anything not on the list
                   opens in the system browser instead.
  Allowed routes . auth pages, /onboarding, /app/live, /app/live/overlay
  Default boot ... #/app/live/overlay (electron/main.cjs:196-203)
  Verdict ........ PARTIAL — functional overlay, but unsigned binaries and a
                   dead preload.ts.

5.1 THE APP SHELL (src/App.tsx:341-458)
---------------------------------------
Two rendering modes:

  MODE A — chromeless. Used when running in Electron, OR when the user is on
  /app/live and the session status is "active" or "paused". Renders only the
  session timeout banner, the network banner, and the page. In Electron it also
  adds an 8px draggable title strip.

  MODE B — full chrome. Skip-to-content link, mobile drawer sidebar with
  backdrop, desktop AppSidebar, AppTopBar, SessionTimeoutBanner, NetworkBanner,
  main content area (max-width 7xl, responsive padding), the SetupChecklist
  banner for users who have not completed onboarding, MobileNav bottom bar, plus
  three global modals: UpgradeModal, AppWalkthrough, InstallPromptModal.

Global keyboard: Ctrl/Cmd+B toggles the sidebar (App.tsx:359-372).

7.4 PAYMENT PROVIDERS
---------------------
BOTH Stripe and Razorpay are wired, and BOTH are shown simultaneously in
SettingsBilling. There is no automatic geo-based provider selection.
  Stripe is considered "configured" on the client when any VITE_STRIPE_PRICE_*
  env var is present (SettingsBilling.tsx:58-64). If not, the upgrade buttons
  are disabled.
  Razorpay is gated by billing_settings.razorpay_enabled (default true) plus the
  RAZORPAY_KEY_ID / RAZORPAY_KEY_SECRET secrets.
  Which one is actually live in production is UNKNOWN from source — it depends
  entirely on which env vars are set.

7.5 STRIPE CHECKOUT — STEP BY STEP
----------------------------------
   1. User clicks upgrade or buy-credits in SettingsBilling.
   2. Client calls createCheckoutSession -> POST create-checkout with price_id,
      success_url, cancel_url, optional coupon_code, and an Idempotency-Key.
   3. Edge function authenticates, rate-limits (Postgres RPC), and validates the
      price against an allowlist built from env vars plus the catalog. Prices
      not on the allowlist are rejected.
   4. Gets or creates the Stripe customer and stores stripe_customer_id on the
      profile.
   5. Creates a Stripe Checkout Session with metadata (plan_id or
      credit_pack_id) and allow_promotion_codes: true.
   6. Client redirects to session.url; the user pays on Stripe's hosted page.
   7. Stripe fires checkout.session.completed to the stripe-webhook function.
   8. Webhook updates profiles (plan or credits), upserts subscriptions, and for
      packs calls the add_credits RPC.
   9. The user returns to /app/settings/billing?checkout=success and the page
      shows a toast and reloads.

  ENTITLEMENTS ARE GRANTED SERVER-SIDE ONLY. The client never writes plan or
  credit values. This is correct and important.

7.6 STRIPE WEBHOOK — WHAT IS HANDLED
------------------------------------
  Event                            Handled  Notes
  -------------------------------- -------  --------------------------------
  checkout.session.completed       yes      plan/pack grant
  invoice.paid                     yes      resets monthly usage, grants credits
  customer.subscription.deleted    yes      downgrades to free
  customer.subscription.updated    yes      syncs status, plan, trial fields
  invoice.payment_failed           yes      grace period, downgrade after 3 tries
  charge.refunded                  NO       not handled at all
  everything else                  logged as unhandled

  Security: HMAC signature verification with a 5-minute replay window;
  idempotency via the idempotency_log table keyed stripe_event_{id}; production
  rejects test-mode events; a missing webhook secret causes a hard 503 rather
  than silently accepting.

  BUG: the invoice.payment_failed branch sets profiles.credits to the absolute
  value 50 (free tier monthly), which can wipe out purchased credit packs
  (stripe-webhook/index.ts:573-574).

7.7 RAZORPAY CHECKOUT — STEP BY STEP
------------------------------------
   1. Client calls createRazorpayOrder with a product_type.
   2. Edge function authenticates, loads billing_settings, validates the product
      type against an enum, and applies a promo code (from the request or from
      profiles.pending_promo_code).
   3. Creates a Razorpay Order in INR and inserts a payment_orders row.
   4. Client loads Razorpay.js and opens the modal.
   5. Only payment.captured is handled by the webhook. It verifies an HMAC
      SHA256 signature, claims an idempotency key, grants the plan/credits
      BEFORE marking the order paid (so a failure can be retried), and records
      the promo redemption. Missing secret -> 503.

  STRUCTURAL LIMITATION: pro_monthly and enterprise_monthly are ONE-TIME Razorpay
  Orders, not Razorpay Subscriptions. There is no auto-renewal, no dunning, and
  the cancel/resume endpoints (which are Stripe-specific) do not apply. Indian
  customers effectively buy one month at a time and must repurchase manually.

7.8 CREDITS SYSTEM
------------------
GRANTS
  Signup ............... handle_new_user trigger grants 50 credits
  Stripe pack .......... add_credits RPC, action 'purchase'
  Stripe renewal ....... add_credits, action 'subscription_grant'
  Razorpay purchase .... add_credits
  Referral ............. record_referral_reward RPC grants both parties
  Promo bonus .......... add_credits with payment id {paymentId}_promo
  add_credits is granted to service_role ONLY — clients cannot call it.

DEDUCTIONS
  The deduct-credits edge function is the authoritative path. It ignores the
  client-supplied cost and re-resolves it server-side via resolveActionCost
  (deduct-credits/index.ts:259-272). Some AI functions deduct inline using the
  same deductCreditsAtomic helper.
  ATOMICITY CAVEAT: deductCreditsAtomic is a JavaScript read-then-conditional-
  update using .gte("credits", amount), not a single SQL transaction
  (_shared/supabase.ts:257-338). The .gte guard prevents going negative, but it
  is weaker than the FOR UPDATE row lock in the original SQL function — and that
  SQL function (deduct_credits) has been revoked from authenticated users, so
  the JS path is what runs.

AT ZERO CREDITS
  The edge function returns HTTP 402 PAYMENT_REQUIRED; the client opens the
  upgrade modal.

CREDIT LEAKS (AI calls that cost money but charge nothing)
  parse-resume ...... no deduction, despite resume_analysis = 12
  gap-analysis ...... no deduction
  parse-document .... no deduction

7.9 IS THERE A MARKETPLACE?  — DIRECT ANSWER: NO
------------------------------------------------
The audit specifically searched for any marketplace, store, or purchasable-
content surface. There are no files matching *marketplace* anywhere in the repo,
and no purchasable items other than subscription plans and credit packs.

What might look like a marketplace but is not:
  ExamPapers.tsx ..... a browser of official exam paper metadata from the
                       exam_papers table. Locked papers mean "questions not
                       ingested yet", not "pay to unlock". Nothing is sold.
  MyQuestions.tsx .... the user's own uploaded questions. Private CRUD.
  UploadQuestions .... an ingest tool. No monetization hooks.
  Question bank ...... shared content, free to use; only the AI features on top
                       of it cost credits.

So the only commerce surfaces in this application are:
  (1) plan subscription via Stripe (USD) or Razorpay (INR, one-time)
  (2) credit pack purchase via Stripe or Razorpay
  (3) promo codes and referral rewards that discount or top up the above

7.11 PLAN GATING — WHERE IT IS AND WHERE IT IS NOT
---------------------------------------------------
SERVER-SIDE (weak)
  requirePlan and requireCapability helpers exist and are called by several AI
  functions. But:
    * PLAN_RANK ranks 'starter' at 0, identical to 'free'. Therefore every
      requirePlan(..., "starter") check — which guards the practice overlay,
      company research, and others — DOES NOT BLOCK FREE USERS.
    * CAPABILITY_MIN_RANK sets nearly every capability to 0, so the capability
      system is a no-op except for priority_models (rank 4).
  The practical effect: a free user with credits can call server endpoints that
  the UI presents as paid-only.

CLIENT-SIDE (real but bypassable)
  planHasFeature / requireFeature in subscriptionManager, PlanGate components,
  useAuth.canAccessFeature with its own smaller FEATURE_PLAN_MAP (which is not
  aligned with the full PLANS.features), and credit pre-checks in
  creditsManager.

ROUTE-LEVEL
  ProtectedRoute blocks the whole /app area if the Stripe subscription is
  past_due beyond a 3-day grace. Razorpay one-time buyers never trigger this.

CONFIRMED GAPS
  Feature                Client blocks free?  Server blocks free?
  ---------------------- -------------------- ---------------------
  Company research       yes                  NO (starter rank = 0)
  Practice overlay       yes                  NO (same reason)
  Calendar sync          yes                  NO server gate found
  mock_test_ai           yes                  no plan check on the

8.9 RATE LIMITING — TWO SYSTEMS, UNEVENLY APPLIED
--------------------------------------------------
  TIER 1 — in-memory Map inside a single Deno isolate. Ineffective across
  instances; the file itself documents this (rateLimit.ts:3-7).
  TIER 2 — Postgres RPC check_rate_limit against the rate_limit_buckets table.
  Effective globally, and FAIL-CLOSED if the RPC errors or times out.

  Adopted the distributed limiter: generate-answer, generate-hint,
  generate-debrief, generate-questions, generate-star-answer,
  polish-star-section, prep-tool, ai-coach-chat, company-research,
  gap-analysis, parse-document, parse-resume, analytics-dashboard,
  bulk-import-questions, all billing/payment functions, session functions,
  delete-account, export-user-data.

  NO RATE LIMIT AT ALL (and several are expensive):
    select-test-questions, generate-practice-questions, collect-exam-papers,
    parse-question-pdf, analyze-test-performance, razorpay-create-order,
    schedule-interview, send-email, sync-calendar, record-referral,
    disconnect-calendar, billing-status.

8.10 FRONTEND CALLS TO NON-EXISTENT FUNCTIONS
----------------------------------------------
  None in production code. The only stale reference is "create-portal-session"
  in a skip-list inside src/lib/network/fetchEdge.ts:18 — it is never invoked.

8.11 ERROR HANDLING, CORS, OBSERVABILITY
-----------------------------------------
  Two parallel error stacks coexist: the modern _shared/errors.ts + auth.ts, and
  the legacy utils.ts errorResponse. Newer endpoints use Zod validation; older
  ones use ad-hoc checks.
  Standard codes: 402 for credits, 429 for rate limit, 503 fail-closed when the
  rate-limit RPC or a webhook secret is unavailable.
  CORS is centralised with an origin allowlist that fails closed in production
  and permits localhost plus Lovable preview origins otherwise.
  Logging is structured JSON with redaction. THERE IS NO SENTRY IN THE EDGE
  FUNCTIONS — only a comment noting it as future work (errors.ts:10). Sentry
  exists on the web client only.

9.1 PROVIDERS AND MODELS
------------------------
  Google Gemini — PRIMARY. Default model gemini-2.0-flash (GEMINI_MODEL_DEFAULT).
    Also used: gemini-1.5-pro, gemini-2.5-flash. Used for hints, answers,
    debriefs, company research, prep tools, document parsing, exam question
    generation, and vision (screenshots and PDFs).
  OpenAI — gpt-4o, gpt-4o-mini, gpt-4-turbo. Default for STAR generation and
    STAR section polish.
  Anthropic — claude-3-5-sonnet-20241022, claude-3-haiku-20240307. Used as a
    resume-parsing fallback and available via model selection.
  OCR.space — last-resort OCR for resumes.
  NOT USED: Groq, and there is no Lovable AI gateway (only Lovable preview
  origins appear in the CORS allowlist).

9.2 MODEL SELECTION AND FALLBACK
---------------------------------
  resolveModel() maps profiles.preferred_model plus profiles.plan_id to a
  concrete API model id. Free plans are FORCED onto Gemini
  (resolveModel.ts:48-57). A per-request model override is accepted by some
  endpoints. The fallback chain is: chosen model -> gemini-2.0-flash ->
  gemini-1.5-pro, with up to 2 retries per model and retry on transient 429/5xx
  (aiProvider.ts:213-267).

9.3 STREAMING
-------------
  Only generate-answer streams. It uses Gemini's streamGenerateContent with
  alt=sse, and wraps OpenAI/Anthropic responses into an equivalent SSE stream.
  The client consumer is streamFunction in src/lib/api/functions.ts:153-271.
  Everything else is request/response JSON.

9.4 PROMPTS
-----------
  Prompts are inline in each edge function, with two shared collections:
  _shared/examAIPrompts.ts for gov-exam question generation, and the tool prompt
  table inside prep-tool/index.ts:60-185. Prompt-injection guards are regex
  patterns in _shared/validators.ts:28-43, duplicated in several functions.
  These guards are best-effort and bypassable — standard LLM risk.

9.5 COST AND TOKEN ACCOUNTING
------------------------------
  ai_usage_logs is written by logAICost() but ONLY from generate-answer,
  generate-hint, generate-debrief, ai-coach-chat, and prep-tool. All other AI
  calls are unlogged.
  model_cost_logs exists as a table and in the generated types but NO EDGE
  FUNCTION EVER WRITES TO IT.
  Cost estimates are hardcoded microcent rates in aiProvider.ts:75-93, not real
  provider billing data. Therefore the admin "AI spend" figures are estimates.

9.6 BYOK (BRING YOUR OWN KEY) — HALF REMOVED
---------------------------------------------
  Product decision: REMOVED. The client explicitly disables it
  (src/lib/api/functions.ts:85-88, src/lib/security/byokVault.ts:1-17), the
  settings page is a deprecation notice with no route, and /app/settings/byok
  redirects to models.
  BUT the server still accepts x-byok-openai, x-byok-anthropic, and
  x-byok-gemini headers and will use them (utils.ts:82-90, gemini.ts:61-67).
  The validate-api-key function that would validate such keys is dead.
  profiles has byok_* columns in the generated types, but no function ever
  encrypts or stores a submitted key — there is no server-side key vault.
  Importantly, BYOK does NOT bypass credit deduction (verified by unit test
  creditsManager.test.ts:91-98).

10.6 THE BIGGEST DATABASE RISK — BASELINE SCHEMA DRIFT

  This is the single most important structural issue in the database.

PART 11 — SECURITY REVIEW
================================================================================

11.1 WHAT IS DONE WELL (do not regress these)
----------------------------------------------
  * Credits are server-authoritative: add_credits and deduct_credits are
    service_role only, client INSERT into credit_transactions is revoked, and
    the deduct endpoint ignores the client's claimed cost.
  * Webhooks verify HMAC signatures, enforce idempotency through a dedicated
    table, reject test-mode events in production, and hard-fail (503) when the
    signing secret is absent rather than accepting unverified payloads.
  * Deepgram keys never reach the browser — a 60-second scoped key is minted
    server-side per session.
  * Profile privilege columns are pinned against escalation, with a separate
    trigger guarding is_admin.
  * Promo code enumeration was closed by dropping the public read policy.
  * Public sharing moved from a broad RLS policy to token-scoped SECURITY
    DEFINER RPCs.
  * CORS fails closed in production.
  * Electron is configured correctly: contextIsolation on, nodeIntegration off,
    sandbox on, a CSP injected via webRequest, will-navigate blocked, and
    window.open denied.
  * The distributed rate limiter fails CLOSED on error.
  * collect-exam-papers uses a host allowlist against SSRF.

11.2 FINDINGS — HIGH
---------------------
H1  SERVER PLAN GATING IS A NO-OP FOR THE 'STARTER' TIER.
    PLAN_RANK: free = 0 and starter = 0 (billingCatalog.ts:47-53). Every
    requirePlan(..., "starter") therefore passes for free users. This guards the
    practice overlay and company research among others.
    Additionally CAPABILITY_MIN_RANK is 0 for nearly every capability
    (requireCapability.ts:24-37).
    IMPACT: a free account with credits can reach paid-only server endpoints.

H2  UNCHARGED AI ENDPOINTS.
    parse-resume, gap-analysis, and parse-document all call paid LLM APIs and
    deduct nothing, despite resume_analysis = 12 being defined in
    creditEconomics.ts. IMPACT: uncapped cost exposure per user.

H3  EXPENSIVE ENDPOINTS WITH NO RATE LIMIT.
    select-test-questions, generate-practice-questions, parse-question-pdf,
    analyze-test-performance, collect-exam-papers, razorpay-create-order,
    send-email, schedule-interview, sync-calendar, record-referral.

H4  COMMITTED PRODUCTION ENVIRONMENT FILE.
    .env.production is tracked in git and contains a live Supabase anon JWT.
    The anon key is designed to be public, but committing environment files
    violates the project's own rule stated in .env.example and creates a habit
    that will eventually leak a real secret.

H5  BASELINE SCHEMA NOT IN MIGRATIONS (see 10.6). RLS status for 12 tables
    cannot be verified or reproduced from source.

11.3 FINDINGS — MEDIUM
-----------------------
M1  BYOK headers still honoured server-side while the feature is removed from
    the client (utils.ts:82-90). Unintended surface.
M2  Gemini API key sent as a URL query parameter in parse-document (line 39) —
    can be captured by proxies and logs.
M3  end-session trusts a client-supplied credits_used value with no
    reconciliation. Currently harmless only because nothing calls it.
M4  Credit deduction is a JS read-then-update rather than one SQL transaction.
    The .gte guard prevents negatives but concurrent requests can interleave.
M5  bulk_update_users is GRANTed to authenticated; the only thing standing
    between a normal user and mass user modification is the in-function
    has_role check. If that function is ever edited carelessly, it becomes a
    privilege escalation.
M6  billing_settings is readable by every authenticated user (using(true)).
M7  exam_papers and exam_images are world-readable with using(true).
M8  user_achievements and model_cost_logs allow authenticated users to INSERT
    their own rows — users could fabricate achievements or cost entries.
M9  Windows binaries are NOT code signed (signAndEditExecutable: false), and
    auto-update ships unsigned artifacts. SmartScreen will warn users, and the
    update channel has weaker integrity guarantees.
M10 release-new/ (~86 MB of installers) is untracked but not gitignored — one
    `git add .` away from being committed.
M11 .env.local contains SERVER secrets (OPENAI_API_KEY, STRIPE_SECRET_KEY,
    SUPABASE_SERVICE_ROLE_KEY, SENTRY_AUTH_TOKEN) inside a frontend project. It
    is gitignored, but service-role keys should not live beside VITE_ variables
    where a naming mistake exposes them to the bundle.
M12 No Sentry in edge functions — backend failures are invisible outside logs.

11.4 FINDINGS — LOW / INFORMATIONAL
------------------------------------
L1  Prompt-injection guards are regex-based and bypassable.
L2  The legacy in-memory rate limiter in utils.ts is per-isolate only.
L3  credit_transactions.stripe_payment_id also stores Razorpay ids — naming
    confusion, not a vulnerability.
L4  Two parallel auth helper patterns (authenticateRequest vs requireAuth) with
    slightly different ban handling.
L5  The session-expiry banner never forces a sign-out.
L6  Electron's View menu exposes Reload/Force Reload in production builds.
L7  Electron update listeners in the preload bridge have no unsubscribe helper.
L8  The stale _asar-extract/ copy of the Electron main process differs from
    source (1440x900 window, port 8080, no overlay IPC) — drift risk if anyone
    treats it as the source of truth.
L9  ai-feedback is dead but fully armed: if it were wired by mistake it would
    start writing scores into session_answers.

The desktop app is deliberately NOT the whole product. It is an overlay client.
It boots directly to #/app/live/overlay, allows only auth, onboarding, /app/live
and /app/live/overlay, and pushes every other route out to the system browser
via ElectronRouteGate.

  predicates (isStripeConfigured etc.).
  MISMATCH: env.ts's AppEnvironment type includes "test" but
  scripts/validate-env.js does not — the direct cause of the CI failure above.

13.5 PWA AND OFFLINE
--------------------
  public/manifest.json plus a minimal service worker (public/sw.js) that caches
  assets only. Registered in src/main.tsx:82-101 and disabled in dev and in
  Electron. usePwaInstallPrompt drives an install prompt modal.
  Offline behaviour: useOfflineFallback, useIsOffline, a NetworkBanner, and the
  live coach falls back to locally generated talking points when AI is
  unreachable. Verdict PARTIAL — real but shallow.

13.6 PERFORMANCE
----------------
  Manual chunking into 11 vendor/app bundles (vite.config.ts:99-138), lazy
  loading for all app pages, eager loading for marketing pages to protect first
  paint, console.log stripped in production, source maps off in production.

13.7 OBSERVABILITY
------------------
  Sentry on the web client (init in main.tsx, source map upload via the Vite
  plugin, capture in GlobalErrorBoundary). PostHog for product analytics with
  opt-out outside production and identify-on-auth. A Supabase health check runs
  at boot. Feature flags come from two places: plan-derived client flags in
  globalStore and DB flags in the feature_flags table.
  NOTE: ErrorBoundary.tsx:51-54 still references a legacy window.__sentry__
  global that no longer exists.

PART 16 — WHAT IS GENUINELY MISSING / NOT BUILT
================================================================================

If someone asks "what does this app NOT do", this is the honest list.

COMMERCE
  * There is no marketplace, no content store, no paid question packs, and no
    seller/creator side. The only things purchasable are plans and credits.
  * No recurring billing in India. Razorpay is one-time orders only.
  * No refund flow for real money.
  * No free trial creation (the plumbing to read a trial exists; nothing starts
    one).
  * No invoicing, no tax/GST handling, no dunning emails.

PRODUCT FEATURES
  * No text-to-speech. The mock interviewer never speaks.
  * No video. Everything is audio and text; there is no camera, no body-language
    analysis, no recording playback.
  * No group practice / peer interviews. The database tables exist
    (practice_rooms, room_chat, room_participants, room_questions) and the RLS
    is written, but WebRTC was never built and the routes redirect away.
  * No global content search — the command palette only navigates.
  * No resume version history browser.
  * No AI generation inside the Answer Bank.
  * No Outlook or Apple Calendar integration.
  * No push notifications and no scheduled email digests or reminders beyond the
    single interview-scheduled email.
  * No mobile app (the web app is responsive; the mobile nav is incomplete).
  * No deep links into the desktop app.
  * No LinkedIn / GitHub / Slack / Zapier integrations — they appear as hidden
    "coming soon" entries in Settings.

CONTENT
  * The gov-exam question bank is effectively empty at ~26 SQL-seeded MCQs.
    The engine is far ahead of the content.
  * Many exam_papers rows have no linked questions and will show as locked.
  * The scraper that would fill the bank is written but not deployed.

ENGINEERING
  * No server-side entitlement enforcement worth the name (see H1).
  * No baseline schema in migrations — the database cannot be rebuilt from
    source alone.
  * No Sentry or APM on the backend.
  * No test coverage for UI, stores, or edge functions.
  * No signed desktop binaries.
  * No working CI (the validate-env step fails on the workflow's own values).
